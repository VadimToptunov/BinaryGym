> Статус: план утверждён (ревизия 2). Срезы 1 и 2 реализованы; следующий — срез 3.
> Цель первого этапа — доказать одно утверждение:
> **«Мы можем надёжно генерировать много уникальных, воспроизводимых, решаемых и автоматически проверенных задач по реверс-инжинирингу».**

## 0. Принятые решения (ревизия 2)

1. **Секрет vs `invert()`.** Сгенерированный секрет — авторитетное решение:
   `secret = generate_secret(...)`, `expected = pipeline.apply(secret)`.
   Решение **не** восстанавливается через `pipeline.invert()`. `invert()` остаётся у обратимых примитивов
   и проверяется свойствами (`invert(apply(x)) == x`), но источником истины не является.
2. **Политики безопасности — у backend'а.** Allowlist импортов и прочие проверки уровня бинарника принадлежат
   backend'у/целевой политике (`LinuxCSafetyPolicy`), а не глобальному валидатору. У C++, Rust, JVM, Android, Swift
   будут совсем другие runtime-зависимости. Валидатор лишь вызывает политику, которую ему передал backend.
3. **Сканирование бинарника на открытый секрет** — это **детектор регрессий/утечек**
   (`plaintext_leak_regression`), и только. Он не доказывает, что задача сложная, защищённая или устойчивая к реверсу.
4. **Шаблонный фингерпринтинг** — крупный продуктовый риск (см. риск 10). Архитектура backend'а не предполагает
   соответствия «checker → один фиксированный шаблон»: у checker'а может быть несколько стратегий рендеринга,
   все сохраняют семантику ChallengeSpec. В срезе 1 — небольшой явный механизм стратегий, без фреймворка.
5. **Расположение кода.** Отдельный репозиторий https://github.com/VadimToptunov/BinaryGym. Проект перенесён
   из подкаталога `binarygym/` репозитория `classroom_scraper` через `git subtree split` с сохранением истории.

### Уточнения по итогам реализации среза 1

- **Стратегия рендеринга не входит в ChallengeSpec.** Она выбирается backend'ом из отдельного подпотока RNG
  (`backend/linux-c/strategy`) и пишется в приватную запись сборки. Spec остаётся backend-независимым.
- **Сложность разделена.** В spec — только семантические размерности; `compiler_complexity` добавляется
  при упаковке (зависит от `-O` и strip).
- **`challenge_id` выводится из содержимого spec** (`bg-` + 16 hex sha256) и проверяется при загрузке —
  подделанная приватная запись отклоняется.
- **Контракт ввода зафиксирован в `reference.py`:** одна строка stdin, обрезка по первому CR/LF/NUL, не более
  255 байт. Валидатор проверяет согласие бинарника с этим контрактом на граничных случаях.
- **Барьер для оптимизатора.** На `clang -O2` детектор `plaintext_leak_regression` поймал реальную утечку:
  компилятор обратил побайтовый пайплайн и положил открытый секрет в бинарник как константу сравнения.
  Исправлено чтением таблицы через `volatile`-указатель; добавлен регрессионный тест на 20 seed × 2 стратегии.
- **Лицензия — MIT** (файл `LICENSE` репозитория, `license = "MIT"` в `pyproject.toml`).

### Уточнения по итогам реализации среза 2

- **Схема v2.** `target` вынесен из ChallengeSpec в `BuildSpec` (`build.py`): платформа, backend, стратегия,
  компилятор и опции. У каждой сборки — свой детерминированный `build_id` (`bgb-…`); логический
  `challenge_id` (`bg-…`) от платформы больше не зависит. Записи схемы v1 не читаются — ошибка с подсказкой
  «перегенерируйте» (конвертер не делали: пользовательских данных ещё нет).
- **Раскладка данных.** Публичный пакет — `generated/<build_id>/`. Приватное —
  `<private>/<challenge_id>/challenge.json` (spec + решение) и `<private>/<challenge_id>/builds/<build_id>.json`
  (BuildSpec + отчёт валидации). По умолчанию `<private>` = `$BINARYGYM_PRIVATE_DIR` или
  `$XDG_DATA_HOME/binarygym/private` (`~/.local/share/binarygym/private`). `doctor` предупреждает,
  если хранилище внутри текущей папки.
- **Версии семейств сохраняются.** `transformation` v1 (XOR/ROL) оставлен рядом с v2, `--family-version`
  выбирает версию. Golden-тест подтверждает: v1 для seed 12345 после рефакторинга даёт тот же секрет и
  `expected`. Golden-тесты закрепляют секрет и хэш checker'а, а не `challenge_id` (он включает
  `generator_version` и меняется с каждым релизом).
- **Единственность ответа проверяется, а не предполагается.** У каждого checker'а есть `accepted_count()`;
  spec отклоняется, если ответов не ровно один. Для `byte_compare` это следует из биективности примитивов
  (проверено свойствами), для конечного автомата — считается динамическим программированием по автомату.
- **Автомату понадобилась проверка длины.** Обратные рёбра позволяют более длинным входам дойти до
  accept (например, «символ + возврат + секрет»), поэтому checker и C-код сначала проверяют длину.
- **Стратегии объявляют применимость.** `fused_loop` не предлагается для пайплайнов с перестановкой,
  `string_compare` — только для открытого ответа (`direct`). Детектор `plaintext_leak_regression`
  пропускается только там, где checker встраивает ответ по замыслу (`embeds_plaintext()`).
- **Правила пайплайна v2.** 3–5 шагов; соседние шаги из одной «группы слияния» запрещены (XOR и
  позиционный XOR сливаются в один XOR); S-box и перестановка — не более одного раза. Генерируемый S-box —
  без неподвижных точек, перестановка — не тождественная.

### Разработка на macOS

6. **На Mac работаем в Linux-контейнере (Docker / OrbStack).** Цель MVP — Linux x86_64 ELF, а нативный
   clang на macOS собирает Mach-O (на Apple Silicon — arm64), и политика `LinuxCSafetyPolicy` (`nm -D`)
   к нему неприменима. Нативная поддержка Mac — это отдельный будущий backend, а не обход в Linux-backend'е.

   ```bash
   # из корня репозитория BinaryGym на Mac
   docker run --rm -it --platform linux/amd64 \
     -v "$PWD":/work -w /work python:3.12 bash

   # внутри контейнера
   pip install -e '.[dev]'
   pytest
   binarygym generate --seed 12345
   ```

   - `python:3.12` (полный образ) уже содержит gcc и binutils; clang опционален
     (`apt-get update && apt-get install -y clang`), иначе используется gcc.
   - `--platform linux/amd64` даёт ровно целевую платформу; на Apple Silicon — через эмуляцию (медленнее).
   - Код правится на Mac, тесты и генерация запускаются в контейнере (каталог смонтирован).
   - Для gdb внутри контейнера: `--cap-add=SYS_PTRACE`. Под эмуляцией на Apple Silicon gdb может быть
     нестабилен; для динамического анализа надёжнее Linux-VM (UTM / Lima) или облачная сессия.
   - Нативно на Mac работают `binarygym verify` (чистый Python) и статический анализ ELF в Ghidra / IDA Free /
     Binary Ninja / Cutter; запустить ELF на macOS нельзя.
   - Альтернатива контейнеру — облачные сессии Claude Code (Linux x86_64, проверено).
   - Не проверено на реальном Mac: это вывод из устройства кода; первая проверка — в начале следующей сессии.

### Совместимость с картой навыков (skill-first roadmap)

Долгосрочная продуктовая карта (документ «BinaryGym — продуктовая карта направлений Reverse Engineering»,
пока вне репозитория) задаёт модель `Skill × Platform × Architecture × Artifact × Difficulty × Strategy × Goal`
и разделение `ChallengeSpec` / `BuildSpec` / `ChallengeArtifact` / `Submission` / `GoalVerifier`.
Проверка кода среза 1 на совместимость с ней:

| Направление | Состояние после среза 1 | Блокирует? |
|---|---|---|
| Одна семантика → разные платформы | `target` лежит в ChallengeSpec и входит в хэш `challenge_id`; семейство жёстко задаёт `linux/x86_64/c` | **Мешает** — исправить в срезе 2 (см. ниже) |
| ChallengeSpec отдельно от BuildSpec | Стратегия, флаги, компилятор уже в приватной записи сборки (`BuildRecord`); id сборки нет | Нет — `BuildRecord` и есть прототип BuildSpec |
| Другие goals (`patch_behavior`, `parse_format`, ...) | Разрешён только `recover_secret`; поле `Secret` обязательно | Нет — схема версионирована; «скрытую истину» обобщаем, когда появится второй goal |
| Другие checker'ы | Поле `checker` типизировано как `ByteCompareChecker` | Нет — union в срезе 2 (запланировано) |
| Submission → GoalVerifier | `verify` принимает строку и вызывает эталон | Нет — одна небольшая функция |
| Валидация других goals | Валидатор построен на пробах stdin и вердиктах SUCCESS/DENIED | Нет — понадобится валидатор на goal |
| Структурная вариативность, AI-мутации | Несколько стратегий + дифференциальная проверка против эталона | Нет — это и есть схема «мутация → проверка эквивалентности» |
| Skill tags, таксономия track/skill/archetype/family/instance | У семейства есть `concepts`; сложность — размерности | Нет — добавляется новыми полями |
| Automation / batch | Детерминированные seed, приватная запись на id | Нет — `generate-batch` тривиален |
| Synthetic malware | Разрешён только `safety_class = benign_re`; политика у backend'а | Нет — дверь закрыта намеренно |

**Вывод:** жёстко блокирующих решений нет. MVP ради карты не рефакторим, кроме одной точки ниже.

**Миграция в срезе 2 (вместе с union checker'ов, одной сменой схемы → `schema_version 2`):**

1. Вынести `target` из ChallengeSpec в BuildSpec (развитие `BuildRecord`): spec описывает только семантику.
2. Убрать выбор платформы из семейства; цель задаётся при сборке (CLI/backend).
3. Ввести id сборки (`build_id`, производный от `challenge_id` + BuildSpec) рядом с логическим `challenge_id`;
   публичный пакет и приватная запись сборки адресуются по нему. Закрывает долг «одинаковый id у gcc- и clang-сборки».
4. Старые приватные записи `schema_version 1` — только чтение с явной ошибкой или одноразовый конвертер
   (решить при реализации; в репозитории пользовательских данных пока нет).

**Уточнения к карте, которые учитываем при проектировании будущих goals:**

- *Patching:* проверка надёжна только с ограничениями — бюджет изменённых байтов и неизменное поведение
  на остальных входах; иначе «патчем» может быть собственная программа, печатающая SUCCESS.
- *Automation:* принимать ответы (например, JSON `id → значение` по скрытому корпусу), а не исполнять
  пользовательские скрипты — иначе нужна настоящая песочница. Для скрытых корпусов — только случайные
  128-битные seed (иначе риск 2: «автоматизация» = перегенерация генератором).
- *Dynamic analysis:* проверка результата простая, но утверждение «задача требует динамического анализа» —
  педагогическая гипотеза, автоматически не проверяется.
- *Obfuscation:* семантическая эквивалентность проверяется автоматически, «полезная сложность vs шум» — нет.
  В матрицу пригодности стоит добавить измерение «проверяема ли педагогическая ценность автоматически».

## 1. Что такое BinaryGym

- **Это:** движок, который процедурно генерирует тренировочные задачи по реверс-инжинирингу. Задача однозначно задаётся семейством, его версией и seed, а проверка ответа автоматическая.
- **Это не:** курс, платформа, SaaS, генератор вредоносного ПО, LLM-генератор бинарников.

Сценарий пользователя:

```
binarygym doctor
binarygym generate --family transformation --seed 12345
./generated/<id>/challenge          # Enter key: ...  →  SUCCESS / ACCESS DENIED
binarygym verify ./generated/<id> MY_ANSWER   # ✓ Correct / ✗ Incorrect
```

Анализ бинарника — внешними инструментами: Ghidra, IDA Free, Binary Ninja, radare2/Cutter, objdump, gdb.

## 3. Архитектура

### 3.1. Общая схема

```
seed ─► Family.generate(rng) ─► ChallengeSpec  (источник истины: JSON, с версией)
                                   │
              ┌────────────────────┼──────────────────────┐
              ▼                    ▼                      ▼
     reference.accepts()     CBackend.render()     family.solution() / hints()
     (эталон на Python)            │                (приватные данные)
              │                    ▼
              │            Compiler → ELF
              │                    │
              └──────► Validator ◄─┘   эталон и бинарник обязаны совпасть на всех входах
                           │
                           ▼
           Package: публичная папка + отдельное приватное хранилище
```

Ключевые принципы:

- **ChallengeSpec — источник истины.** C-код — всего лишь артефакт, его всегда можно сгенерировать заново.
- **Семейство генерирует spec, а backend рисует не семейство, а checker** (тип проверки).
  Новое семейство переиспользует готовые checker'ы. Новый backend (JVM, PE, Wasm) реализует только checker'ы и примитивы и ничего не знает о семействах.
- **Эталонный вычислитель (reference evaluator)** — Python-реализация той же логики. Через него работают и валидация, и `verify`.

### 3.2. ChallengeSpec

Модель — `dataclasses` (frozen) с явными `to_dict` / `from_dict` и проверкой входа.
**Почему не Pydantic:** spec небольшой, явная сериализация прозрачнее, и это минус одна зависимость. Если схема разрастётся, можно перейти позже.

Поля:

| Поле | Назначение |
|---|---|
| `schema_version` | версия формата spec |
| `generator_version` | версия BinaryGym |
| `id` | идентификатор задачи |
| `family`, `family_version` | семейство и его версия |
| `seed`, `options` | всё, что нужно для воспроизведения |
| `goal` | `recover_secret` |
| `target` | `platform` / `arch` / `language` — только данные, логика spec от них не зависит |
| `secret` | `alphabet`, `length`, `value` |
| `checker` | тип проверки (см. ниже) |
| `difficulty` | размерности сложности и эвристическая метка |
| `safety_class` | пока всегда `benign_re` |

Варианты `checker`:

- `ByteCompare(pipeline: [Transform...], expected: bytes, checksum: Optional)`
- `StateMachine(states, transitions, start, accept)`

Пример (сокращённо):

```json
{
  "schema_version": 1,
  "generator_version": "0.1.0",
  "family": "transformation",
  "family_version": 1,
  "seed": 12345,
  "goal": "recover_secret",
  "target": {"platform": "linux", "arch": "x86_64", "language": "c"},
  "secret": {"alphabet": "A-Za-z0-9_", "length": 12, "value": "..."},
  "checker": {
    "kind": "byte_compare",
    "pipeline": [
      {"op": "xor", "key": 91},
      {"op": "rol", "bits": 3},
      {"op": "sbox", "table": [/* 256 */]}
    ],
    "expected": "hex...",
    "checksum": {"kind": "sum16", "value": 4711}
  },
  "difficulty": {"transformation_complexity": 3, "structural_complexity": 1, "compiler_complexity": 0, "label": "beginner"},
  "safety_class": "benign_re"
}
```

Требования к spec: сериализуемость, детерминизм, версионирование, тестируемость и независимость от C-backend.

### 3.3. Примитивы преобразований

Все примитивы — в одном модуле. Разделим, когда вырастет.

| Примитив | Концепт для учащегося |
|---|---|
| XOR с константой | побайтовое обратимое преобразование |
| XOR с ключом, зависящим от позиции | ключевой поток, индексация |
| ADD / SUB по модулю 256 | арифметика с переполнением |
| ROL / ROR | битовые операции |
| S-box (таблица подстановки) | lookup-таблицы |
| Перестановка позиций | переупорядочивание данных |
| Checksum / аккумулятор | **только дополнительное условие**, не преобразование |

У каждого примитива есть:

- `generate(rng)` — детерминированно генерирует параметры;
- `apply(bytes)` — эталонная реализация;
- `invert(bytes)` — обратное преобразование; проверяется свойствами и гарантирует единственность ответа (биекция), но решение из него **не** строится — авторитетен сгенерированный секрет;
- C-рендер в backend;
- метаданные `concept`;
- тесты (Hypothesis: `invert(apply(x)) == x`).

Криптографию не используем: задача в том, чтобы учить реверсу, а не изображать сложность.

### 3.4. Семейства (MVP)

1. **`direct`** — beginner. Секрет лежит в бинарнике открыто, сравнение побайтовое. `strings` помогает — так и задумано.
2. **`transformation`** — 2–4 обратимых примитива из пула, затем сравнение с ожидаемыми байтами и необязательная контрольная сумма. От seed зависят секрет, константы, таблицы, порядок операций и имена переменных.
3. **`state_machine`** — автомат, сгенерированный по seed. Из каждого состояния вперёд ведёт ровно один символ, остальные уводят в тупик, поэтому ответ единственный. Варианты представления в C: таблица переходов или `switch`.

`ChecksumFamily` как отдельное семейство не делаем: одна контрольная сумма не даёт единственного ответа (см. риск 1). Checksum живёт как условие внутри `transformation`.

Реестр семейств — обычный словарь `FAMILIES = {...}`, без плагинной системы.

### 3.5. Детерминированная случайность

- Собственный **SplitMix64** (~20 строк) вместо `random.Random`. Причина: поведение `random.Random` не гарантировано между версиями Python.
- **Подпотоки** выводятся как `hash(seed, label)`. Так новая случайная выборка в одной части генератора не сдвигает остальные.
- Внутри детерминированного ядра запрещены глобальный `random`, `time` и `os.urandom`. Тест подменяет их через monkeypatch и падает при любом вызове.
- Golden-тест фиксирует хэш spec для известных seed. Если хэш поменялся, это требует явного повышения `family_version`.
- Если `--seed` не задан, seed берётся из ОС (128 бит) **вне** детерминированного ядра и сохраняется в приватные данные.

### 3.6. Компиляция

- `Compiler` (Protocol) → `NativeCompiler`: ищет clang, потом gcc.
- `compile(source, target, options) -> BuildArtifact` возвращает путь, sha256, компилятор, версию, флаги, stdout и stderr.
- Опции: `-O0` / `-O1` / `-O2`, `--strip`.
- Для воспроизводимости: фиксированное имя `challenge.c`, `-ffile-prefix-map`, без `-g`, `SOURCE_DATE_EPOCH`, сборка в изолированной временной папке.
- Static linking по умолчанию не используется: `glibc-static` есть не везде.

### 3.7. Запуск сгенерированных программ

- `Runner` (Protocol) → `SubprocessRunner`.
- Есть timeout, временный рабочий каталог и урезанное окружение (`PATH`, `LC_ALL=C`), ввод подаётся через stdin.
- Протокол сделан так, чтобы позже можно было подключить bwrap / nsjail / контейнер, не меняя вызывающий код.
- Допущение безопасности: программы генерируются только нашими шаблонами из allowlist примитивов. Runner — это защита в глубину, а не основной барьер.

### 3.8. Валидация (обязательна перед упаковкой)

Успешная компиляция ничего не доказывает. Задача публикуется только после того, как пройдены все шаги:

1. Сгенерировать spec.
2. Взять правильный ответ — сгенерированный секрет (не `invert`).
3. Проверить его эталоном.
4. Сгенерировать C и скомпилировать.
5. Запустить бинарник с правильным ответом и проверить, что результат `SUCCESS` и код возврата 0.
6. Запустить с N неправильными входами (случайные, с отличием в один байт, короче, длиннее, пустой) и проверить отказ.
7. Проверить, что эталон и бинарник **согласны на каждом входе**.
8. Проверить, что зависание обрывается по timeout.
9. Детектор регрессий `plaintext_leak_regression`: секрета в открытом виде в бинарнике быть не должно (кроме `direct`). Это ловит ошибки генератора/оптимизатора, но **не** доказывает сложность или стойкость.
10. Применить политику безопасности **backend'а** (для Linux/C — `LinuxCSafetyPolicy`: allowlist динамических импортов `fgets`, `puts`, `printf`, `strlen`, `memcmp`…). Валидатор не знает конкретных правил — их задаёт backend.
11. Только после этого — упаковка.

### 3.9. Публичные и приватные метаданные

```
generated/<id>/            ← можно отдать участнику
    challenge
    README.md
    metadata.json          ← только публичные поля

.binarygym/private/<id>.json   ← никогда не отдаётся
```

| Публичное | Приватное |
|---|---|
| id, family, family_version | seed |
| platform, arch, goal | secret |
| эвристическая сложность, концепты | полный ChallengeSpec |
| sha256 бинарника | решение, подсказки |

- Публичные метаданные — отдельный тип данных, который строится из явного списка полей (allowlist). Это не «spec минус секретные поля».
- Тест сканирует все публичные файлы на наличие секрета, seed и фрагментов spec.
- Такое разделение напрямую переносится на будущий сервер: приватные данные остаются на сервере, наружу уходит только публичная папка.

### 3.10. Verify

- `binarygym verify <id-или-путь> <ответ>`: берёт id из публичного `metadata.json`, загружает приватный spec и проверяет ответ **эталонным вычислителем** («принимается ли вход»), а не сравнением строк.
- Вывод — `✓ Correct` / `✗ Incorrect`. При неверном ответе ничего не раскрывается.
- Бинарник не запускается и не анализируется.

### 3.11. CLI

Typer: одна зависимость, типизированные аргументы, нормальная справка.

```
binarygym generate --family transformation [--seed N] [--optimization O0|O1|O2] [--strip] [--out DIR]
binarygym verify <challenge> <answer>
binarygym inspect <challenge> [--private]      # по умолчанию только публичное
binarygym list-families
binarygym doctor                               # компилятор, версии, тестовая сборка и запуск
```

`generate-batch` — по сути цикл по seed. Добавляем, только если он укладывается в несколько строк.

### 3.12. Сложность

- Хранится как **размерности**: `transformation_complexity`, `structural_complexity` (ветвления, размер автомата), `compiler_complexity` (оптимизация, strip), `has_lookup_tables`.
- Пользователю показывается `Estimated difficulty: Beginner / Intermediate (heuristic)`.
- Модель данных оставляет место для эмпирической сложности (успешность, медианное время, использование подсказок, доля брошенных попыток). Телеметрию не реализуем.

### 3.13. Подсказки и решение (закладываем структуру)

- `family.hints(spec) -> list[HintStage]` — структурированные этапы, выведенные из spec, а не придуманные LLM.
- `family.solution(spec)` — машиночитаемое описание решения: длина входа, стадии, параметры.
- Обе вещи приватные. Позже из них можно получить объяснения, материалы для преподавателя и контекст для AI-тьютора.

### 3.13a. Стратегии рендеринга

Вариативность бывает двух видов:

- **параметрическая** — секрет, константы, таблицы, параметры операций;
- **структурная** — цикл vs развёрнутый код, вспомогательные функции, табличная логика, `switch`,
  разная декомпозиция одного checker'а, разная раскладка control flow.

Backend хранит для каждого типа checker'а **список стратегий** (`checker → стратегия A | B | C`).
Стратегия выбирается детерминированно из seed (отдельный подпоток RNG), записывается в приватную запись сборки
и не входит в ChallengeSpec (spec остаётся независимым от backend'а). Валидатор проверяет согласие с эталоном
для любой стратегии — это и есть гарантия сохранения семантики. В срезе 1 — две стратегии для `byte_compare`.

### 3.14. Будущие backend'ы

Spec не содержит платформенных предположений, поэтому новый backend = реализация `render(checker)` для своих checker'ов и примитивов + свой `Compiler`:
`WindowsCBackend`, `MacOSBackend`, `JVMBackend`, `DotNetBackend`, `WasmBackend`, `AndroidKotlinBackend`, `AndroidJNIBackend`, `IOSBackend`. В MVP ничего из этого не реализуется.

## 5. Порядок работы

**Срез 1 — сквозной путь (доказательство концепции):**
`rng` → `spec` → XOR и ROL → семейство `transformation` → C backend → компилятор → runner → валидатор → упаковка → `generate` / `verify`.
Срез готов, когда реально сгенерирована, скомпилирована, запущена (правильный и неправильный ввод) и проверена задача, а повторная генерация с тем же seed даёт идентичный spec.

**Срез 2 — ширина** ✅ (реализовано, см. «Уточнения по итогам реализации среза 2»): остальные примитивы, семейства `direct` и `state_machine`, команды `inspect [--private]`, `doctor`, `list-families`.
В той же смене схемы (`schema_version 2`): `target` → BuildSpec, `build_id` — см. «Совместимость с картой навыков» в разделе 0.
**Приватное хранилище — вне рабочей папки:** по умолчанию `~/.local/share/binarygym/private` (с учётом
`XDG_DATA_HOME`) вместо `./.binarygym/private`, переопределяется `--private-dir`. Причина: ИИ-агент с доступом к
файлам рабочей папки (например, Claude Desktop с filesystem MCP рядом с Ghidra MCP) прочитает ответ вместо реверса;
человеку это тоже лишний соблазн. В README — правило: агенту и участнику отдаётся только публичная папка.
`doctor` и `generate` должны проверять хост: если ОС/архитектура не совпадают с целью backend'а (например,
macOS или arm64 для `linux-c`), сразу выдавать понятную ошибку с подсказкой про Docker, а не падать на валидации.
Проверять также наличие `nm` (binutils).

**Срез 3 — надёжность и документация:** golden-тесты, проверка побитовой идентичности бинарника на одном toolchain, README / ARCHITECTURE / SAFETY.

После каждого среза: тесты, ruff, mypy, реальная генерация, компиляция и запуск с правильным и неправильным вводом, отчёт о результатах.

### Критерии готовности MVP

- `binarygym doctor` сообщает, что окружение готово.
- `binarygym generate --family transformation --seed 12345` создаёт `challenge`, `README.md`, `metadata.json`.
- Бинарник запускается и решается реверсом.
- В публичном пакете нет ответа.
- `verify` корректно принимает и отклоняет ответы.
- Тот же seed даёт тот же логический spec.
- Работают три семейства.
- Все тесты проходят.

## 6. Безопасность (основа для SAFETY.md)

Три зоны:

1. **Образовательный реверс** — то, что делает MVP.
2. **Синтетические malware-подобные упражнения** — в будущем. Любое «опасное» поведение заканчивается симуляцией, например `simulator.record(NetworkIntent(host="training.invalid"))` вместо реального соединения. Домены — только `.invalid` / `.example`.
3. **Реальная вредоносная функциональность** — запрещена всегда: кража данных, разрушительные действия, закрепление в системе, распространение, повышение привилегий, удалённое выполнение команд, реальный C2, обход средств защиты, эксплуатация.

Техническое подкрепление (а не только документ):

- backend генерирует код только из allowlist примитивов и шаблонов;
- у каждого backend'а своя политика безопасности уровня артефакта; для Linux/C — allowlist импортов (нет сокетов, `exec*`, работы с файлами вне stdio);
- поле `safety_class` в spec; классы помимо `benign_re` потребуют отдельного ревью.

План будущих безопасных malware-упражнений: извлечение закодированной фиктивной конфигурации, восстановление фиктивного протокола, расшифровка обфусцированных строк, определение симулированных возможностей, связь между сэмплами, распаковка синтетического контейнера, деобфускация безвредных скриптов. Пакетная генерация (`generate-batch`) даст упражнения на автоматизацию: Ghidra-скрипты, IDAPython, собственные парсеры.

## 7. Риски

| # | Риск | Почему важно | Мера |
|---|---|---|---|
| 1 | **Неоднозначность ответа** | Необратимый пайплайн (например, только checksum) примет несколько входов: бинарник скажет SUCCESS, а `verify`, сравнивающий со строкой, — Incorrect | В `recover_secret` только обратимые примитивы, checksum — только доп. условие; `verify` спрашивает эталон «принимается ли вход»; валидатор проверяет согласие эталона и бинарника |
| 2 | **Подбор seed вместо реверса** | Генератор открытый: при маленьком seed можно перебрать seed, сравнить sha256 бинарника и узнать ответ без реверса | Без `--seed` используется 128-битный seed из ОС; явный seed в документации помечен как «воспроизводимо, но раскрываемо»; id не выводится из одного seed |
| 3 | **Утечка ответа через артефакты** | Имена вроде `secret`/`key` в нестриппнутом бинарнике, имя исходника, пути, README, metadata | Нейтральные сгенерированные имена; фиксированное `challenge.c`; публичные метаданные по allowlist; тест сканирует все публичные файлы; детектор регрессий `plaintext_leak_regression` (не доказательство стойкости) |
| 4 | **Побитовая воспроизводимость** | Между версиями clang/gcc бинарники различаются | Жёсткая гарантия — только логический spec; побитовая идентичность проверяется на одном toolchain и не обещается; версия компилятора пишется в метаданные |
| 5 | **Оптимизатор раскрывает ответ** | При `-O2` компилятор может свернуть константы и фактически вычислить секрет | Детектор регрессий `plaintext_leak_regression` в валидаторе; при необходимости `volatile` или вычисление ожидаемого значения из входа, а не наоборот |
| 6 | **Ввод и кодировки** | Пробелы, кавычки, `\n`, длина буфера: правильный ответ «не проходит» из-за shell | `fgets` с фиксированным буфером, обрезка `\n`, алфавит секрета без пробелов и спецсимволов |
| 7 | **Дрейф генератора** | Правка семейства незаметно меняет задачи для старых seed | Golden-тесты; изменение вывода требует повышения `family_version` |
| 8 | **Ложная «сложность»** | Метрики не отражают реальную трудность для человека | Метка явно названа эвристикой; хранятся размерности; место под эмпирические данные |
| 9 | **Переусложнение** | Соблазн строить платформу вместо доказательства идеи | Жёсткие non-goals; словарь вместо плагинов; минимум зависимостей |
| 10 | **Шаблонный фингерпринтинг** | Если варьируются только параметры, опытный пользователь учится узнавать шаблоны BinaryGym, а не реверсу вообще; задачи «решаются» скриптом по сигнатуре | Явное разделение параметрической и структурной вариативности; несколько стратегий рендеринга на checker; стратегия выбирается из seed; валидатор гарантирует семантическую эквивалентность. В MVP стратегий мало — риск признан и отслеживается |
| 11 | **Решение с помощью ИИ** (LLM + Ghidra/IDA через MCP) | Простые задачи (как `transformation` среза 1 — один цикл XOR/ROL) агент, вероятно, решает за секунды; правильный ответ перестаёт доказывать навык человека. Оценка не проверена экспериментом | Не гнаться за «ИИ-стойкостью» (гонка вооружений, ведёт к обфускации-шуму); позиционировать BinaryGym как тренажёр, а не экзамен — локально запретить ИИ нельзя; приватные данные хранить вне рабочей папки (срез 2); измерять, а не гадать — режим бенчмарка (дорожная карта, п. 8) |

Сознательно **не делаем**: реестр плагинов, абстрактные фабрики, отдельный IR-компилятор, Pydantic, async, `ChecksumFamily` как самостоятельное семейство.

## 9. Дорожная карта после MVP

1. Больше примитивов и семейств в рамках Linux/x86_64 (control-flow flattening, простая обфускация, патчинг бинарника).
2. ARM64 и x86, режимы strip и оптимизации как оси сложности.
3. Структурированные подсказки в CLI (`binarygym hint`).
4. `generate-batch` и упражнения на автоматизацию реверса.
5. Новые backend'ы: Windows PE, macOS (`MacOSCBackend`: Mach-O arm64/x86_64, своя политика импортов через `nm -u`/`otool`), JVM, .NET, Wasm, Android.
6. Синтетические malware-подобные упражнения — по правилам раздела 6.
7. Серверная модель хранения приватных данных, эмпирическая сложность.
8. **Режим бенчмарка для ИИ-реверсеров** (LLM + Ghidra/IDA/Binary Ninja через MCP). BinaryGym даёт то, что нужно
   для честной оценки агентов: свежие экземпляры без утечки в обучающие данные, автоматическую проверку (`verify`),
   градуированную сложность по измерениям (где агент ломается: `-O`, strip, длина пайплайна, стратегия рендеринга),
   структурную вариативность (обобщает агент или узнаёт шаблон — риск 10 становится измеримым) и пакетную генерацию.
   Архитектурных изменений не требует: агент получает только публичный пакет, ответ проверяет `verify`.
   Побочный эффект — первый эмпирический сигнал сложности, с оговоркой: сложное для ИИ ≠ сложное для человека.
9. **Учебный трек «работа с ИИ-ассистентом»** (идея): задачи, где агент склонен ошибаться, а человек должен
   проверить и опровергнуть его выводы.
10. **Агент как дымовой тест генератора** (идея): если задача решается одним `strings` или агентом за один шаг,
    это сигнал, что семейство/стратегия слишком тривиальны.
